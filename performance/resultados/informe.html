Pruebas de rendimiento de Insightful Games con k6

Web y app móvil a través de los WAF y los reverse proxies · corrida del 2026-11-23 · rama feature/waf-compose-unico

Pendiente.

Objetivo y alcance

Medir cuánto tráfico aguanta la aplicación en este equipo antes de dejar de cumplir sus objetivos de tiempo de respuesta, cómo se comporta ante subidas bruscas y qué componente se satura primero. Las peticiones entran por las mismas puertas que los usuarios reales: los WAF por HTTPS, luego los reverse proxies, los gateways y los servicios.

Se pruebaCómo
Web (navegador)Páginas con renderizado en el servidor (/, /historial, /estadisticas) y la API que llama el navegador: perfil, estadísticas, historial (en paralelo, como el frontend) y detalle de una partida.
App AndroidLa API del gateway móvil: inicio (/home), historial, detalle, estadísticas y, en el 30 % de las sesiones, una partida local corta (crear, 4 jugadas y rendirse).
Partidas contra el botPor WebSocket seguro (WSS), con 1, 2, 4, 8 y 12 partidas simultáneas.
Inicio de sesiónA 20 intentos/s desde una sola IP, por encima del límite de los reverse proxies.

No se prueba: el multijugador en línea (necesita dos jugadores coordinados por WebSocket), el análisis del tutor (asíncrono), la descarga de JavaScript y CSS del frontend, ni la interfaz de la app Android.

Entorno

EquipoLaptop con Intel Core i7-10750H (6 núcleos, 12 hilos) y 15,9 GB de RAM, Windows 11
DockerDocker Desktop 29.9.3 sobre WSL 2: la máquina virtual tiene 12 CPU y 7,7 GB de RAM
Sistema probado22 contenedores de compose.yaml: 2 WAF (ModSecurity + OWASP CRS), 2 reverse proxies, frontend SSR, 2 gateways, 9 servicios, 2 workers, RabbitMQ y 4 bases de datos
EntradasLas mismas que los usuarios: https://localhost:8443 (web) y https://localhost:8444 (app), con TLS 1.3 y el certificado validado (CA de mkcert instalada en Windows)
Generador de cargak6 2.4.0 en el mismo equipo que el sistema
Memoria libre al empezar2,0 GB de 15,9 GB, con 3,3 GB en el archivo de paginación (Edge 3,1 GB y VS Code 2,3 GB abiertos)
Aviso sobre el entorno. El sistema y el generador de carga corren en el mismo portátil, y al empezar quedaban solo 2 GB de RAM libres. Se decidió hacer las pruebas igual y documentar el efecto: cuando Windows se queda sin memoria pagina la máquina virtual de Docker y la congela por momentos, lo que aparece como peticiones de varios segundos que no se deben a la aplicación. La sección «Salud del entorno» separa ese ruido usando una sonda que no ejecuta nada de la aplicación.

Diseño de las pruebas

PruebaUsuarios virtuales (VUs)DuraciónPara qué
Humo1 web + 1 móvil1 minComprobar que todos los recorridos funcionan (todas las sesiones móviles juegan) y calentar el sistema.

Bot1, 2, 4, 8 y 12 partidas, 90 s cada nivel7,8 minCapacidad del motor (Botcito) y del WebSocket.
Login20 intentos/s (tasa constante)1 minComprobar el límite de 10/s por IP de los reverse proxies.
  • Mezcla: el 60 % de los VUs navega la web y el 40 % usa la app. Cada VU hace pausas de 1 a 3 s entre acciones (tiempo de una persona leyendo o pensando), así que 40 VUs generan unas 30 peticiones/s, no 40.
  • Usuarios: 50 cuentas de prueba (perf_001 a perf_050) con al menos 3 partidas cada una. Las sesiones se abren antes de cada prueba y despacio, porque el login tiene un límite de frecuencia que, si no, frenaría la propia prueba.
  • Medición: k6 registra cada petición. Un monitor anota cada 3 s la CPU y la memoria de cada contenedor, la CPU del equipo y de k6, la memoria paginada de Windows y el tiempo de una sonda trivial (/health).

Cómo repetir las pruebas

winget install GrafanaLabs.k6             # una vez
pip install psutil                          # para el monitor de recursos
docker compose up -d                        # stack con los WAF y los certificados (docs/secure-channel-tls.md)
.\performance\ejecutar.ps1                 # toda la batería (~40 min); o -Pruebas carga,bot
python performance\informe.py               # genera performance\resultados\informe.html
msedge --headless --no-pdf-header-footer --print-to-pdf=docs\pruebas-rendimiento-k6.pdf performance\resultados\informe.html

Los scripts de k6 están en performance/k6/ y los resultados en performance/resultados/ (los CSV por petición y los tokens no se versionan).
